## 2. Filosofía actual del Constructor IA

Decisión oficial:
- El Constructor IA debe trabajar con **interpretación natural + diálogo de aclaración**.
- El usuario no debe conocer JSON, variables internas ni nombres técnicos de propiedades.
- La IA debe:
  1. interpretar lo seguro;
  2. inferir lo razonable;
  3. mostrar qué entendió;
  4. preguntar sólo cuando exista una ambigüedad real;
  5. permitir revisar;
  6. confirmar;
  7. aplicar al canvas.

No seguir ampliando un parser rígido frase por frase.

El usuario puede escribir lenguaje humano:
- “Mandar a Compras para revisar la factura”
- “Publicar en la cola Pedidos quiero un mate”
- “Usar una cola llamada Pedidos y después leer un mensaje”

y el sistema debe resolver lo posible sin exigir sintaxis técnica.

## 3. Sintaxis de precisión opcional — decisión nueva validada

Se incorporó una ayuda universal opcional:

`Nombre = valor`

NO es obligatoria.
NO reemplaza lenguaje natural.
Sirve cuando el usuario quiere ser explícito.

Ejemplos:
- `Rol = COMPRAS`
- `Usuario = Usuario1`
- `Título = Revisar factura`
- `Origen = Prueba`
- `Instancia = actual`

Para varios datos puede usarse `;`:
`Origen = Prueba; Instancia = actual`

Reglas:
- El usuario trabaja con nombres humanos.
- El contrato/capa común traduce a propiedades internas.
- Nunca exigir `${wf.instanceId}`, `usuarioAsignado`, `RolDestino`, etc.
- Si el valor referencia un dato conocido, resolverlo con Datos disponibles/catálogo.
- Si es ambiguo, preguntar.

Ejemplo validado:
`Publicar en la cola Pedidos con origen = Prueba; instancia = actual.`

Resultado interno:
{
  "origen": "Prueba",
  "instancia": "${wf.instanceId}"
}

El usuario NO tuvo que escribir `${wf.instanceId}`.

Frase validada:
`Crear una tarea. Rol = COMPRAS; Título = Revisar factura.`

Resultado:
`Inicio → Revisar factura → Fin`

Inspector:
- Título = `Revisar factura`

- no preguntar destino;

### Por Usuario

Nueva regla de producto:
El usuario NO debe necesitar escribir dominio Windows.

Frase validada:
`Crear una tarea. Usuario = Usuario1; Título = Revisar factura.`

El Constructor busca contra usuarios activos reales (catálogo/WF_User).

Si existe una coincidencia única:
`Usuario1` → internamente `OMARD\USUARIO1`

Resultado:
`Inicio → Revisar factura → Fin`

Inspector:
- Rol vacío
- Usuario asignado = `OMARD\USUARIO1`
- Título = `Revisar factura`

Reglas:
- No inventar `OMARD\`.
- Resolver usando catálogo real.
- Aceptar UserKey completo también.
- Aceptar nombre visible si identifica un usuario único.
- Si varias coincidencias: preguntar.
- Si no existe: preguntar/ofrecer válidos.

### Rol + Usuario simultáneos

Ejemplo:
`Crear una tarea. Rol = COMPRAS; Usuario = Usuario1; Título = Revisar factura.`

Esto NO debe resolverse silenciosamente.

Debe:
- marcar ambigüedad real;
- preguntar quién debe recibir la tarea;
- mostrar destinos reales;
- al elegir uno, dejar un único destino válido;
- redibujar propuesta;
- quedar aplicable.

Se verificó que el diálogo funciona y permite elegir el destino real.

## 9. PENDIENTE PRIORITARIO — NO pasar todavía a control.if

Al final de la sesión Omar recordó algo importante:

`human.task` no es sólo “crear una tarea”.

Hay que revisar antes de considerar C2B funcionalmente completo:

1. Tarea humana simple.
2. Resultado `APTO`.
3. Resultado `NO_APTO`.
4. Resultado `RECHAZADO`.
5. Mecanismo `volver atrás` / backtrack a una tarea humana anterior.

Conocimiento histórico del proyecto:
- human.task publica resultados como `wf.tarea.resultado`
- también existe resultado específico por nodo `wf.tarea.<nodeId>.resultado`
- APTO / NO APTO fueron validados previamente en flujos reales.
- Existe mecanismo `wfBack` con conceptos como:
  - `frameId`
  - `taskNodeId`
  - `returnToNodeId`
  - `cycle`
- Objetivo del backtrack:
  - un rechazo puede volver a una tarea humana solicitante previa;
  - misma instancia;
  - mismos documentos/contexto;
  - múltiples ciclos;
  - auditoría preservada.

IMPORTANTE:
- No asumir cómo está implementado HOY.
- Inspeccionar ZIP nuevo.
- No dar por hecho que `RECHAZADO` es simplemente `NO_APTO`.
- No empujar automáticamente esta semántica a `control.if`.
- `RECHAZADO` + volver atrás pertenece conceptualmente a semántica de tarea humana y debe estudiarse como tal.
