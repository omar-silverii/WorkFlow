## 2. Filosofía vigente del Constructor IA

Decisión oficial permanente:
- El Constructor IA debe trabajar con **interpretación natural + diálogo de aclaración**.
- El usuario no debe conocer JSON, nombres internos de propiedades ni variables técnicas.
- La IA debe:
  1. interpretar lo seguro;
  2. inferir lo razonable;
  3. mostrar qué entendió;
  4. preguntar sólo cuando exista una ambigüedad real;
  5. permitir revisar;
  6. confirmar;
  7. aplicar al canvas.

No seguir ampliando un parser rígido frase por frase.

Frase y Paso a paso pueden tener interfaces distintas, pero deben converger en:
- la misma semántica;
- la misma capa contractual;
- el mismo nodo técnico válido;
- sin duplicar defaults o reglas en JS y C#.

Regla reforzada hoy:
- **Paso a paso no debe volver a interpretar como lenguaje libre los valores ya elegidos por el usuario en un editor estructurado.**
- Títulos, mensajes, descripciones, paths, payloads y otros valores ya elegidos son DATOS declarativos, no nuevas intenciones.
- Ejemplo validado:
  - Logger Warn
  - Message = `Informar`
  - `Informar` permanece texto y NO dispara `util.notify`.

Sintaxis de precisión opcional:
`Nombre = valor`

Sigue siendo:
- opcional;
- nunca requisito;
- traducida internamente a propiedades reales;
- resuelta contra catálogos/Datos disponibles cuando corresponda.

## 4. Trabajo de hoy — Human Task completo

### 4.1 FIX84C2Bg inicial — SUPERSedido

Se exploró inicialmente la idea de distinguir `NO_APTO` y `RECHAZADO` dentro del Constructor.

La prueba real mostró que ese enfoque mezclaba dos niveles:

Conclusión final:
**esa versión conceptual NO es la línea vigente.**

No tomar `FIX84C2Bg` inicial como cierre funcional.


### 4.2 Decisión de producto final sobre Human Task

En el **diseño del workflow / Constructor IA**, Human Task tiene resultados de flujo:

- `APTO`
- `NO_APTO`

En la **ejecución real de una instancia**, la página de tarea humana puede ofrecer además:
- `RECHAZAR / volver atrás`

El rechazo/backtrack:
- NO pertenece al contrato de construcción de Human Task.
- NO debe aparecer como una tercera rama del Constructor.
- Depende del estado real de la instancia.
- Se resuelve operativamente desde la tarea en ejecución.
- Usa el mecanismo existente de `WF_Tarea_Detalle` / `wfBack`.
- No se rediseñó ni tocó ese runtime.

Regla de lenguaje de diseño:
- frases como “si Compras la rechaza” se interpretan como resultado negativo del diseño → `NO_APTO`;
- NO como backtrack.

No asumir que la palabra humana “rechaza” de una definición equivale al valor técnico runtime `rechazado`.


### 4.3 FIX84C2Bg2 — APTO / NO APTO como salidas hermanas

Se corrigió la representación funcional de Human Task.

Modelo correcto:

Human Task
- APTO → continuación normal
- NO_APTO → rama negativa

No deben aparecer APTO y NO_APTO como pasos en serie.

Se corrigió también que:
- el título explícito `Título = Revisar factura` no absorba la oración siguiente;
- no aparezca una segunda pregunta artificial de SI/NO cuando la acción ya estaba expresada.

Regresión:
- `C2Bg2 = 3/3` VALIDADO.


### 4.4 FIX84C2Bg2b — advertencia explícita en rama humana

Prueba real detectó que:
`registrar una advertencia indicando que debe corregirse`

estaba generando una duda artificial:
- notificación;
- Logger;
- tarea.

Decisión:
- `registrar una advertencia` → `util.logger` con Level `Warn`
- sin preguntar innecesariamente.

También se corrigió la comparación entre:
- borrador funcional;
- grafo técnico interno.

El borrador funcional puede ocultar el `control.if` técnico de `wf.tarea.resultado`, pero el canvas final mantiene ese nodo.

Regresión:
- `C2Bg2b = 1/1` VALIDADO.


### 4.5 FIX84C2Bg2c — Paso a paso Human Task APTO/NO APTO

Se detectó que Paso a paso armaba correctamente la estructura APTO/NO_APTO, pero luego volvía a convertirla en una frase intermedia y una validación legacy reabría preguntas SI/NO.

Corrección:
- Paso a paso conserva su estructura elegida.
- No reconstruye las ramas desde la frase descriptiva.
- APTO/NO_APTO convergen al mismo tramo semántico que Frase.
- Se colapsa el `Fin` duplicado cuando las ramas ya convergen.

Regresión:
- `C2Bg2c = 1/1` VALIDADO.


### 4.6 FIX84C2Bg2d — valores declarativos de Paso a paso

Prueba real:
- Logger Warn
- Message = `Informar`

El sistema volvía a interpretar la palabra `Informar` como intención de notificación.

Corrección general:
- si el origen es Paso a paso, valores de propiedades ya elegidas son DATOS;
- no vuelven a entrar a detectores de intención/ambigüedad;
- la misma palabra escrita como Frase libre sigue siendo interpretable normalmente.

Regresión:
- `C2Bg2d = 1/1` VALIDADO.

Validación manual final de Human Task:
- Human Task COMPRAS / Revisar Factura.
- APTO → Fin.
- NO APTO → Logger Warn.
- Message = `Informar`.
- Sin preguntas artificiales.
- Al crear workflow:
  - `human.task`
  - `control.if` técnico sobre `wf.tarea.resultado == apto`
  - true → Fin
  - false → Logger Warn → Fin.

Conclusión:
**Human Task queda cerrado en esta etapa.**
