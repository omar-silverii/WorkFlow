# 3. Filosofía oficial del Constructor IA

Decisión permanente:

**Frase natural + diálogo de aclaración.**

El usuario no debe aprender:

* JSON;
* nombres internos de propiedades;
* variables técnicas;
* nombres técnicos de nodos;
* sintaxis rígidas del parser.

El sistema debe:

1. interpretar lo seguro;
2. inferir solamente lo razonable;
3. mostrar qué entendió;
4. preguntar cuando exista ambigüedad real;
5. permitir revisar;
6. confirmar;
7. aplicar al canvas.

No continuar construyendo un parser rígido frase por frase.

### Frase y Paso a paso

Pueden tener interfaces diferentes, pero deben terminar en:

* la misma semántica;
* la misma capa contractual;
* el mismo nodo técnico válido;
* los mismos parámetros normalizados.

### Regla crítica de Paso a paso

**Paso a paso NO vuelve a interpretar como lenguaje natural los valores que el usuario ya eligió mediante controles estructurados.**

Una vez elegido un valor, es un dato declarativo.

Aplica a:

* mensajes;
* títulos;
* paths;
* payloads;
* nombres de variables;
* valores de variables;
* contenidos;
* roles;
* usuarios;
* parámetros de nodos.

La frase inferior generada por Paso a paso es sólo una descripción auxiliar.

**No es fuente de verdad para reconstruir el workflow.**

# 5. Trabajo de hoy — FIX84C2D1 / D1b / D1c — util.notify

## Objetivo

Integrar `util.notify` al camino contractual común:

**Frase ↔ Paso a paso → misma semántica → mismo nodo `util.notify`.**

### Decisiones de producto

El Constructor NO debe inventar decisiones de negocio.

Para `util.notify`:

Defaults técnicos seguros:

* tipo/canal interno;
* nivel `info`;
* prioridad `normal`.

Datos reales:

* destino;
* rol/usuario;
* mensaje.

El asunto puede usar el default contractual:

`Notificación`

si el usuario no especifica uno.

---

## FIX84C2D1 inicial

Se agregó el contrato común de `util.notify`.

Regresión inicial:

`1/3`

Fallaban:

* notificación por rol;
* notificación por usuario corto.

`19 / 0 / 0`.

El provider legacy volvía a interpretar datos internos de la notificación como nuevas intenciones.

* `rol COMPRAS` podía disparar Human Task;
* `revisión disponible` podía generar señales de tarea;
* contenido como `factura aprobada` podía contaminar otros detectores.

---

## FIX84C2D1b

Se corrigió el problema general:

**los datos declarados dentro de una notificación no vuelven a participar en la detección de otros nodos.**

El fix no modificó los tests que habían fallado.

Resultado:

# 7. FIX84C2D3 / D3b — file.read

## Objetivo

Integrar `file.read` al camino común.

### Reglas contractuales

`path` es decisión real y obligatorio.

No inventar una ruta ficticia.

Defaults técnicos seguros:

* salida = `archivo`
* JSON = No
* encoding = `utf-8`
* compresión = Auto
* cache = Sí

`path`, `salida` y `zipEntry` son datos declarativos.

Una ruta puede contener palabras que coincidan con nombres de acciones y sigue siendo solamente una ruta.

Ejemplo:

`C:\temp\Notificar_COMPRAS.txt`

no debe crear una notificación.

---

`3/4`

# 11. Lecciones arquitectónicas reforzadas hoy

Durante D1, D3 y especialmente D4 apareció repetidamente el mismo tipo de defecto:

un nodo se resolvía correctamente, pero capas posteriores volvían a interpretar sus valores como nuevas intenciones.

Se detectaron distintas capas:

* provider ML legacy;
* fallback visual;
* `fallbackNeedsHelp`;
* validaciones de consistencia guiada;
* normalización previa al canvas.

Regla general que debe preservarse:

## Una vez que un fragmento de lenguaje fue absorbido como propiedad de un nodo resuelto, deja de ser texto libre para detectar otras intenciones.

Esto aplica especialmente a:

* mensajes de Notify;
* contenidos de File Write;
* paths de File Read;
* valores de State Vars;
* títulos y mensajes de Human Task;
* propiedades estructuradas de Paso a paso.

No resolver esto agregando excepciones frase por frase.

Resolverlo por responsabilidad semántica.
