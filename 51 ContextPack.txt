3. DECISIÓN OFICIAL DEL CONSTRUCTOR IA
======================================================================

Dirección oficial y permanente:

INTERPRETACIÓN NATURAL CON DIÁLOGO DE ACLARACIÓN.

Se aplica a todos los nodos actuales y futuros, Constructor IA por frase,
Constructor paso a paso, Datos disponibles, plan estructurado, validación,
contrato/fingerprint y banco de regresión.

El usuario no debe tener que conocer:
- JSON;
- sintaxis ${...};
- variables internas;
- nombres técnicos exactos de nodos;
- nombres internos de propiedades;
- propiedades de handlers;
- una gramática artificial.

La frase puede ser breve, incompleta, ambigua, aproximada, expresada con
palabras diferentes a las internas y sin indicar explícitamente Inicio o Fin.

El sistema debe:
1. Interpretar todo lo que pueda con seguridad.
2. Diferenciar resolved / inferred / ambiguous / missing / unrecognized.
3. Mostrar qué entendió.
4. Mostrar qué infirió.
5. No inventar silenciosamente decisiones importantes.
6. Preguntar solamente lo necesario.
7. Resolver dudas mediante controles guiados y editables.
8. Regenerar el plan después de cada respuesta.
9. Mostrar resumen final comprensible.
10. Permitir revisión.
11. Exigir confirmación real.
12. Aplicar al canvas solamente cuando el plan esté resuelto.

El modo paso a paso continúa siendo el camino determinista.
La frase es un acelerador y una conversación, no un lenguaje técnico disfrazado.

4. REGLAS NUEVAS DE LENGUAJE NATURAL VALIDADAS EN ESTA SESIÓN
======================================================================

A. EL USUARIO NO DEBE CONOCER NOMBRES DE PROPIEDADES

Incorrecto como requisito humano:
"publicar en la cola Omar con payload quiero un mate"

Correcto:
"publicar en la cola Omar quiero un mate"

o:
"crear una cola llamada Omar y publicar quiero un mate"

El sistema entiende que el contenido posterior a la intención de publicar
corresponde técnicamente al contenido/payload del nodo.
El usuario expresa QUÉ quiere hacer y QUÉ contenido usar; el contrato decide
DÓNDE se guarda técnicamente.

B. NO INVENTAR ESTRUCTURA JSON INNECESARIA

"publicar quiero un mate" puede ser texto simple.
No inventar automáticamente {"mensaje":"quiero un mate"}.

Si el usuario expresa campos, por ejemplo:
"publicar con origen Prueba e instanceId el de esta instancia"
puede construirse contenido estructurado con esos campos.

C. REFERENCIAS CONTEXTUALES

Una vez presentado un objeto, una acción posterior puede referirse a él sin
repetir el nombre.

"Usar una cola llamada Pedidos, publicar número 123 y después leer un mensaje."
Debe interpretarse:
- publicar en Pedidos;
- consumir/leer de Pedidos.

Si el usuario nombra otra cola explícitamente, se respeta el nuevo referente.

D. INICIO Y FIN IMPLÍCITOS

No exigir:
"Quiero iniciar un flujo..."
ni:
"Después finalizar."

El sistema agrega util.start y el util.end normal como estructura.
Excepción: un final explícito de rama sí tiene significado funcional.

E. VERBOS DEPENDEN DEL CONTEXTO

La palabra "leer" sola no debe crear doc.load.
- "leer un mensaje" → queue.consume;
- "leer un archivo" → file.read;
- "leer una factura" → documental;
- "leer una nota de crédito" → documental;
- "leer un documento" → documental.

F. FRASES DE REGRESIÓN HUMANAS

No escribir frases para facilitar el parser.
Evitar como requisitos técnicos: payload, ${...}, queue.publish, queue.consume,
propiedades internas, "quiero iniciar un flujo", "después finalizar".

G. PREGUNTAR SOLO ANTE AMBIGÜEDAD REAL

"Quiero crear una cola llamada Omar y publicar quiero un mate."
La acción posterior aclara el contexto operativo: no preguntar por infraestructura.

"Quiero crear una cola llamada Infra y publicar en la cola Operativa un aviso."
Usa dos colas distintas: sí corresponde aclarar qué significa crear Infra.
