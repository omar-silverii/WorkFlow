1. MÉTODO OFICIAL Y PERMANENTE DE DESARROLLO
======================================================================

Este método debe mantenerse en todas las sesiones futuras.

Omar no tiene que conocer previamente cómo debe resolverse técnicamente un
sistema de workflows ni entregar una especificación completa.

Omar puede comenzar con:

- una idea mínima;
- una necesidad de usuario;
- una duda;
- un problema observado;
- una pregunta sobre qué le falta al producto;
- o una intención todavía incompleta.

Responsabilidad del asistente como ingeniero del sistema:

1. Leer completo el ContextPack y el Prompt.
2. Esperar el ZIP completo cuando corresponda.
3. Inspeccionar primero los archivos reales.
4. Reconstruir el estado desde el ZIP y no desde recuerdos.
5. Analizar el problema como producto, no solamente como código.
6. Investigar productos similares, prácticas profesionales o información
   actual cuando aporte valor a la decisión.
7. Proponer cómo debería funcionar el sistema.
8. Detectar implicaciones operativas:
   - quién lo usa;
   - qué permisos requiere;
   - dónde queda registrado;
   - qué trazabilidad deja;
   - qué ocurre en estados cerrados;
   - qué errores o casos límite existen;
   - qué falta para que sea productivo.
9. Presentar alternativas cuando exista una decisión real.
10. Recomendar una dirección y explicar por qué.
11. Conversar la propuesta con Omar antes de implementar.
12. Incorporar la experiencia de Omar como usuario final.
13. Insistir cuando exista un camino claramente mejor.
14. Ser honesto y crítico; no ser complaciente para evitar una discusión.
15. Implementar solamente después de acordar la dirección.
16. Trabajar con cambios mínimos, precisos y comprobables.
17. Validar con un caso operativo real de punta a punta.
18. Cerrar la etapa con ContextPack y Prompt actualizados.

La conversación natural entre Omar y el asistente es parte del método.

No se requieren fichas, formularios ni especificaciones técnicas obligatorias.
El asistente debe aplicar internamente la disciplina de inventario, alcance,
dependencias, agrupación, riesgo y regresión sin trasladar esa carga a Omar.

Distribución de responsabilidades:

- Omar aporta la necesidad, la experiencia real de uso, las correcciones de
  producto y la decisión final.
- El asistente aporta investigación, ingeniería del sistema, propuesta
  funcional, arquitectura compatible con el proyecto real, análisis técnico,
  implementación y criterio profesional.
- Ambos refinan la solución mediante la conversación previa al código.

Ciclo de trabajo habitual:

1. Omar plantea la idea o el problema.
2. El asistente analiza qué significa para el producto.
3. Se inspecciona el ZIP y el código real.
4. El asistente informa qué existe, qué falta y qué recomienda.
5. Se conversa y acuerda la solución.
6. El asistente propone el primer grupo o fix.
7. Se genera ZIP de reemplazo.
8. Omar compila y prueba en su entorno real.
9. Se corrigen únicamente problemas demostrados.
10. Se cierra y documenta la etapa.

Esta decisión se aplica a:

El usuario no debe tener que conocer:

- JSON;
- sintaxis ${...};
- nombres internos de variables;
- nombres técnicos exactos de nodos;
- propiedades de handlers;
- ni una gramática artificial.

La frase del usuario puede ser:

- breve;
- incompleta;
- ambigua;
- aproximada;
- o expresada con palabras distintas a las internas del sistema.

El sistema debe:

1. Interpretar todo lo que pueda con seguridad.
2. Separar el resultado en:
   - resuelto;
   - inferido;
   - ambiguo;
   - faltante;
   - no reconocido.
3. Mostrar claramente qué entendió.
4. No inventar silenciosamente decisiones importantes.
5. Preguntar solamente lo necesario.
6. Ofrecer controles guiados y editables para resolver las dudas.
7. Regenerar el plan después de cada respuesta.
8. Mostrar un resumen final comprensible.
9. Permitir revisar y editar el plan.
10. Aplicar al canvas solamente después de una confirmación real.

Secuencia de producto deseada:

No entiendo perfecto
→ muestro lo entendido
→ pregunto lo necesario
→ el usuario decide
→ genero el plan válido
→ muestro resumen final
→ el usuario confirma
→ aplico al canvas.

El modo paso a paso continúa siendo el camino determinista y seguro.

La frase funciona como acelerador e inicio de una conversación, no como un
lenguaje técnico disfrazado.

Cada nodo deberá declarar, conceptualmente:

- parámetros obligatorios;
- parámetros opcionales;
- tipo de cada parámetro;
- valores predeterminados seguros;

- valores que nunca deben inferirse sin preguntar;
- datos disponibles que puede consumir;
- salidas que deja disponibles;
- validaciones;
- resumen legible;
- pregunta de aclaración cuando falte un dato;
- control guiado para resolverlo;
- reglas de seguridad;
- forma de generar el plan estructurado;
- casos de regresión.

El mismo contrato debe alimentar:

- Constructor paso a paso;
- interpretación por frase;
- diálogo de aclaración;
- Datos disponibles;
- resumen del plan;
- validación funcional;
- contrato/fingerprint;
- banco de regresión.

Objetivo:

Agregar un nodo nuevo no debe requerir construir otra lógica artesanal e
independiente para cada pantalla.

Proceso deseado para un nodo futuro:

1. Implementar o confirmar runtime e inspector.
2. Registrar el nodo en el catálogo.
3. Declarar su contrato de construcción asistida.
4. El modo paso a paso usa ese contrato.
5. El intérprete natural puede proponerlo.
6. Las dudas se resuelven con el mismo contrato.
7. Las salidas alimentan Datos disponibles.
8. La regresión prueba resolución directa y con diálogo.

5. LÍMITE DEL ENFOQUE ANTERIOR
======================================================================

Los fixes 83 a 83d demostraron que el sistema puede reconocer frases técnicas y
generar correctamente nodos de colas.

También demostraron un límite:

Una frase como:

"Quiero iniciar un flujo, publicar en la cola banco-fix83 con payload
{...}, luego consumir 1 mensaje..."

funciona, pero obliga al usuario a conocer:

- queue.publish;
- queue.consume;
- payload;
- JSON;
- ${wf.instanceId};
- ${queue.hasMessage};
- ${queue.messageId};
- ${payload};
- y el orden técnico completo.

Eso es un lenguaje controlado, no una conversación natural.

Una frase humana real puede ser:

"Iniciar, crear una cola Banco-fix83 con wf.instanceId como instanceId y
Prueba por frase como origen, luego crear un log con los mensajes del payload."

Esa frase contiene ambigüedades reales:

- "crear una cola" puede significar crear infraestructura o publicar;
- no indica con certeza si hay que consumir;
- "mensajes del payload" puede significar registrar el enviado, el recibido,
  el objeto completo o algunos campos.

El sistema profesional no debe ignorar ni inventar esas decisiones.

Debe explicar lo entendido y preguntar, por ejemplo:

- ¿Querés publicar en una cola existente?
- ¿Querés registrar el mensaje enviado o consumirlo primero?
- ¿Querés registrar el payload completo o campos específicos?

No continuar agregando indefinidamente expresiones regulares y sinónimos como
solución principal.

Las reglas existentes pueden mantenerse como soporte transitorio, pero la
dirección principal debe ser el contrato universal más diálogo.

11. BANCO DE REGRESIÓN FUTURO
======================================================================

El banco deberá distinguir:

1. RESOLUCIÓN DIRECTA
   La frase tiene información suficiente y genera plan sin preguntas.

2. RESOLUCIÓN CON DIÁLOGO
   La frase es natural o incompleta.
   Debe validarse:
   - qué interpretó;
   - qué duda generó;
   - qué opciones ofreció;
   - qué respuesta eligió la prueba;

3. PROTECCIÓN CONTRA INFERENCIAS PELIGROSAS
   El sistema debe preguntar antes de inventar:
   - destinatarios;
   - tablas;
   - conexiones;
   - rutas;
   - operaciones destructivas;
   - condiciones;
   - resultados humanos;
   - credenciales;
   - estructuras de datos sensibles.

Las frases de regresión no deben ser solamente frases artificiales escritas para
el parser.

Deben incluir maneras humanas, breves, incompletas y alternativas de expresar
la misma intención.
